## 1. Scop

Contabilul firmei primește din Administrativo, pentru o lună aleasă, **un fișier pe care
îl importă direct în programul lui**, în loc să tasteze bonurile de pe foile de parcurs.
Fișierul conține costurile flotei:

- alimentările de pe foile de parcurs (`fuel_entries`);
- cheltuielile din F7 (`vehicle_expenses`: combustibil fără foaie, parcare, spălătorie,
  taxe de drum, pod, TollRo, altele);
- intervențiile de service din F7 (`vehicle_service_entries`), **doar în jurnal, nu în
  note** (vezi decizia L4).

Patru ieșiri, toate de pe aceeași rută și din același model pur:

| Cod format     | Ce primește contabilul                                                                                                                                                                                                   | Pentru cine                                                       | Cât de sigur e formatul                                         |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------- |
| `jurnal_csv`   | Jurnalul de costuri: un rând per cost, cu vehiculul, documentul, baza, TVA-ul, regimul fiscal, conturile PROPUSE și starea „intră / nu intră în notă, cu motiv”                                                           | orice program; e și „previzualizarea” celorlalte                 | e al nostru, deci sigur                                         |
| `articole_csv` | Articole contabile simple: `Data; Nr. doc; Cont debit; Cont credit; Suma; Explicație`                                                                                                                                     | programele cu import din foaie de calcul și mapare de coloane     | coloanele sunt cele din ecranul Saga „Articole contabile” (§4)  |
| `winmentor`    | ZIP cu `NoteContabile.txt` (`TipDocument=NOTA CONTABILA`) și, dacă e cazul, `Partner.txt`                                                                                                                                 | WinMentor (meniul „Import date din alte aplicații”)               | structura e verificată pe documentația producătorului (§4)      |
| `saga`         | ZIP cu `F_<cif>_<nr>_<data>.xml` (câte o intrare „bon de casă cu cod fiscal” per bon cu CUI), `NC_<de-la>_<până-la>.dbf` (articole contabile pentru restul) și `de-verificat.csv`                                       | Saga C, versiunea desktop (Saga WEB nu are importul, §4)          | XML: verificat pe manualul actual; DBF: documentație secundară din 2020, import după actualizarea 598 neconfirmat ⚠ (E8, R10) |

Exportul **propune**, nu înregistrează: nu alocă număr de registru, nu scrie nimic în bază
și nu pretinde că nota e definitivă. Contabilul vede conturile înainte de descărcare și le
poate schimba.

## 2. De ce

- **Planul o cere** (F12, „export în formatul Saga/WinMentor”), iar utilizatorul a cerut pe
  12 oct toate cele opt extensii.
- **E munca pe care contabilul o face azi de mână.** Bonurile fiscale care îndeplinesc
  condițiile unei facturi simplificate sunt exceptate de la RO e-Factura (§4, E15), deci nu
  vin automat în Saga ca e-facturile. Excepția NU acoperă factura emisă de stație la cerere,
  pe baza bonului (vezi §10, „bon + factură”). Un utilizator de pe forumul Saga, 19 ianuarie
  2026, citat literal: „Am clienti de ride sharing - flote cu multe masini, deci cu multe
  bonuri de combustibil. Eu mi-am facut un fisier dbf din care import in conta aceste
  bonuri, sa nu bag manual chiar si 1000 de bonuri lunar.” (§4, E9).
- **Pachetul lunar din F8 rămâne „de citit”.** XLSX-ul și PDF-urile foilor le citește un
  om. Fișierul de aici îl citește programul de contabilitate.
- **Precedentul există și merge:** `src/app/api/export/salarizare/nota/route.ts` scoate nota
  de salarii în CSV, cu conturile luate din setări (`0061_salarizare_conturi_nota.sql`) și
  cu poarta „debit = credit”. F12g refolosește forma: model pur în `src/domain/`, ruta
  subțire, conturile ca DATE.

  dacă totalBani === 0                         → exclusă „sumă zero”
  dacă sursa === "service" și !include_service  → exclusă „factură — vine prin SPV” (L4)
  dacă peCardDeFlota                            → exclusă „card de flotă — factura vine prin SPV” (L5)

  dacă !firma.platitorTva                        → un articol „total”: cont / contDecontare

    cota = cotaTvaLa(linie.data) × coeficientul categoriei
    dacă cota === null                           → problemă blocantă (nu se ghicește)
    baza = round(total / (1 + cota)); tva = total − baza
    (după F12a) dacă cuiFurnizor === null        → tvaDed = 0, tvaNeded = tva (L13)
    regim = regimDeclarat ?? (masaMaximaKg > 3500 ? "integral" : configurare.regimImplicit)

      baza                                   → D cont / C contDecontare           (rol "baza")
      tvaDed                                 → D 4426 / C contDecontare           (rol "tva_deductibil")
      tvaNeded                               → D (pe_cheltuiala ? cont : contTvaNeded) / C contDecontare
                                                                                  (rol "tva_nedeductibil", L8)

export function inAscii(text: string, lungimeMaxima?: number): string {
  const curat = text
    .replace(/[„”“]/gu, '"').replace(/[‚‘’]/gu, "'").replace(/[–—]/gu, "-")

**`src/lib/unelte/dbf.ts`** (dBase III, E20):

```ts
export type CampDbf =
  | { nume: string; tip: "C"; lungime: number }
  | { nume: string; tip: "N"; lungime: number; zecimale: number }
  | { nume: string; tip: "D" };

export function scrieDbf(
  campuri: readonly CampDbf[],
  randuri: readonly (readonly (string | number | DateString | null)[])[],
  dataActualizare: DateString,
): Uint8Array {
  // antet 32 B: [0]=0x03; [1..3]=an-1900, lună, zi; [4..7]=nr. înregistrări (LE);
  //   [8..9]=32 + 32·n + 1 (LE); [10..11]=1 + Σ lungimi (LE); [29]=0x00; restul 0
  // descriptor 32 B per câmp: nume ASCII ≤ 10, completat cu 0; [11]=tip; [16]=lungime
  //   (D = 8); [17]=zecimale
  // 0x0D după descriptori
  // înregistrare: 0x20, apoi C la stânga cu spații, N la dreapta cu spații și punct
  //   zecimal (toFixed), D = AAAALLZZ, null = spații
  // 0x1A la final
  // Aruncă dacă: un C depășește lungimea DUPĂ inAscii, un N nu încape, un octet > 0x7E.
}
```

Aruncarea la depășire e deliberată: un câmp tăiat tăcut ar muta toate câmpurile
următoare. Explicația se taie ÎNAINTE, în `format-saga.ts`, cu `inAscii(…, 48)`.

- Toate selecturile cu LITERAL, ca `coloane.test.ts` să le verifice față de

  explicația spune „vehicul necunoscut”. La `org_admin` nu se întâmplă decât pentru

  await requireFeature(tenant.organizationId, "fleet");
  const permisiuni = await getPermissionMap(tenant.organizationId, tenant.role, tenant.memberId);

  if (!can(permisiuni, "vehicles:export", "all"))
    return raspunsText("Nu aveți dreptul de a exporta datele flotei.", 403);
  if (!can(permisiuni, "vehicles:read", "all") || !can(permisiuni, "trip_sheets:read", "all"))
    return raspunsText(
      "Exportul contabil cere acces la tot parcul și la toate foile: cu acces doar la echipă, " +
        "nota ar ieși incompletă fără să se vadă.",
      403,
    );

  const parsat = schemaExportLa(todayInBucharest()).safeParse(
    Object.fromEntries(new URL(cerere.url).searchParams),
  );
  if (!parsat.success) return raspunsText(motiveZod(parsat.error), 400);
  // `raspunsText` e LOCAL în ruta notei de salarii (nu se exportă), iar `motiveZod` NU
  // există în cod: ambele se scriu aici (motiveZod = mesajele `issues`, câte unul pe linie,
  // cu numele câmpului), sau se mută într-un modul comun în același commit.

  // organizations: cui, platitor_tva — .eq("id", tenant.organizationId)
  // liniiDeCostPeLuna → construiesteArticole
  // 0 linii → 404 „Nicio cheltuială a flotei în luna aleasă.”
  // probleme blocante → 409 cu lista (ca nota de salarii)
  // format → corp + content-type + nume; antetul `cache-control: ANTET_CACHE_DESCARCARE`
}

### 13.1 Ce s-a schimbat

**Fapte externe**

- **E15 înlocuit.** Sursa era o speță fiscalitatea.ro din 2024, dinaintea OUG 138/2024, care
  spunea chiar contrariul pentru bonurile peste 100 euro. Acum: OUG 120/2021 art. 10 alin. (1),
  pe consolidarea din 01.06.2026 — bonurile fiscale care îndeplinesc condițiile unei facturi
  simplificate (art. 319 alin. 12, 13, 21) sunt exceptate de la RO e-Factura. Premisa „bonul nu
  vine prin SPV” e acum verificată pe text, dar cu o limită nouă: factura cerută pe baza
  bonului NU e exceptată (rând nou în §10, R2).
- **E16–E19 mutate pe consolidarea curentă a Codului fiscal** (08.08.2026,
  `DetaliiDocument/312601`). Forma citată, 01.07.2026, nu mai era ultima. Textele art. 291,
  298, 25 și 319 sunt identice cu ce afirma specificația. **19% de la 01.01.2017** e acum
  verificat pe consolidarea din 04.04.2025 (era ⚠).
- **E19 întărit:** cerința CIF-ului cumpărătorului pe factura simplificată e chiar în
  Codul fiscal, art. 319 alin. (21) lit. f), nu doar în norme. Rămâne ⚠ existența ordinului
  pentru alin. (13).
- **E8 slăbit:** firul de pe forum NU confirmă un import DBF reușit după actualizarea 598.
  Arată un utilizator care nu-și vedea fișierul și un sfat să aleagă `*.*`. Nici „răspunsuri
  ale echipei” nu se poate verifica. Am adăugat R10.
